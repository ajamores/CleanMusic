# A Source names one Track by default; playlist expansion is explicit

A Source URL identifies **one Track** by default. The common way a user reaches Muzik is standing on a single song in YouTube and copying the address bar — which routinely carries a trailing `list=…` (an autogenerated radio, `RD…`, or whatever playlist the song was played from). The intent is the song, not the queue it happened to play in. So the default is single: yt-dlp's `noplaylist=True`, which drops the attached `list=` whenever the URL also names a video. Downloading the whole list from such a link floods the library with tracks the user never asked for — the concrete failure that motivated this decision.

Expanding a playlist is therefore **opt-in**, via a per-run `--playlist` switch. It is deliberately *not* a saved setting (unlike `--format`): playlist-vs-single is an intent about *this* URL, not a standing preference. Default off.

**A pure-playlist URL in single mode is refused, not guessed.** yt-dlp's `noplaylist` only collapses a URL that names *both* a video and a list; a bare playlist URL (`playlist?list=PL…`, or `watch?list=RD…` with no `v=`) has no single video to fall back to, so `noplaylist` is ignored and the whole list would expand. Rather than silently pick one arbitrary track or silently expand, single mode **refuses** such a URL with a clear message — *"that's a playlist; pass `--playlist` to download all of it."* The refusal hands the choice back to the user instead of the tool deciding for them.

Crucially, the "is this a playlist?" verdict comes from **yt-dlp's own classification** of the URL, not from Muzik parsing the URL itself. Muzik does no home-grown URL inspection (no regex for `v=` / `list=`); it asks yt-dlp what the link is and acts on that. Keeping URL semantics inside yt-dlp is the whole point — the address formats are yt-dlp's to understand, and they change.

## Considered alternatives

- **yt-dlp's own default (expand playlists)** — rejected: it is exactly the flood this decision exists to prevent; a shared song link should not import a hundred tracks.
- **Single-mode silently takes the first track of a bare playlist** — rejected: it honours "always one track" with zero URL-reading, but returns an arbitrary track with no signal that a playlist was collapsed. A refusal is louder and safer.
- **`--playlist` as a saved setting (like `--format`)** — rejected: "always expand playlists" is not a preference anyone holds; the intent is per-link.
- **A download-count cap (`--limit N`)** — not adopted: the user expands only their own playlists, so an arbitrary cap adds friction for no real risk. (A bare radio URL under `--playlist` is effectively unbounded, but that is not a real workflow; revisit if it becomes one.)

## Consequences

- The default single-song path is **free of custom URL logic** — it is `noplaylist=True` and yt-dlp does the collapsing. This is the user's primary flow and carries no Muzik-specific parsing to rot.
- The bare-playlist refusal needs a lightweight pre-flight classification (ask yt-dlp the URL's type before downloading), so the run stops *before* pulling any tracks rather than after.
- `--playlist` is a per-invocation CLI boolean; it maps to `noplaylist=False` and is never persisted to settings.
- No entry cap is enforced; a `--playlist` run downloads the full list. If unbounded radio expansion ever becomes a real path, a cap is a later, additive decision.
